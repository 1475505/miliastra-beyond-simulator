# 接入、跨步骤决策与恢复

首次进入或恢复会话时读本文件，再按 [Skill 的步骤索引](../SKILL.md#按需读取)只读当前步骤。本文件负责接入、子智能体检查、产物位置、恢复和回退；操作细节在各步骤文档中。

## PREFLIGHT — 接入与基线

PREFLIGHT 只做盘点，不计入七步：

1. 盘点用户的想法、参考图、已有 Lua、GIA、存档和反馈；读工作区 `AGENTS.md`。
2. 按[知识库发现与可用性核验](#知识库发现与可用性核验)检查已配置的资料来源，再判断缺什么。不要一开始就让用户装插件或提供文档。
3. 检查本会话实际可用的模拟器、浏览器、美术工具和子智能体。目录存在或已安装不等于会话可见；MCP、Web、Harness 接入方式不同，以当前宿主的说明和 schema 为准。
4. 已有工程：读游戏卡片、策划案、production-plan、测试、最近的试玩记录、存档和源码，找出本轮目标和最早缺少的证据，据此确定当前步骤。
5. 在 `docs/production-plan.md` 记录当前步骤、目标、退出证据和阻塞项。只建本次任务需要的文件，不为未开始的步骤建占位文件。

新游戏的顺序：策划案 → HTML → TDD 用例 → 美术 → Lua → 测试 → 真机。

## 知识库发现与可用性核验

开始制作前检查一次，范围限于本任务所需。恢复会话时复用已记录的来源；工具、资料版本或涉及的 API 有变化时才复核。

1. **查工作区入口。** 从 `AGENTS.md`、README、项目索引及其引用处寻找官方 Lua API、客户端脚本使用指南、控件/模板与脚本挂载说明、已知问题和真机记录，并查看项目内的 Skill、MCP、插件配置。本地知识库可能在被 Git 忽略的目录，按已知目录定向检索，不扫全盘。
2. **查宿主配置与能力目录。** 优先用宿主提供的插件、MCP、Skill 列表；必要时读项目级/用户级配置，只看相关的名称、启用状态、资源入口和本地路径。寻找 `miliastra-toolbox` 系列（如 `dsh-plugin-miliastra-toolbox`）、其他知识库服务和本地文件知识库。插件可能用别名，不凭名称判断覆盖范围；不改配置，不回显令牌和无关内容。
3. **核验内容。** 确认会话能调用或读取候选来源后，定向读一段官方 Lua API 和相关指南：内容须属于千星客户端 2D UI + Lua，且能读到函数签名、参数/枚举和操作说明。不为核验而加载整套文档。只有 3D 节点图资料、只有检索摘要或缺接口表的来源，不算取得所需资料。
4. **记录。** 在 production-plan 记录来源名称、工具或路径、文档标题、可查到的版本/日期、适用范围和读取结果。状态分三级：已配置 / 本会话可读 / 已取得所需官方资料。配置读不到或工具未加载时记“尚未核实”或“当前不可用”，不推断用户没有配置。官方文档、实战经验、真机观察、模拟器策略分开标注；版本冲突时先核对来源，不拼凑签名。
5. **复用优先，只问缺项。** 资料够用就继续；连接不可用但本地资料够用时，改用本地资料并记录。确实缺少本轮所需内容时，简要说明缺哪份资料或哪项能力，请用户启用连接、提供路径或补充文档。缺资料时仍可做步骤 1–4，依赖缺失 API 的 Lua 要等资料补齐。

向用户只简述可用来源和实际缺项，不列全部配置。模拟器工具和知识库分别检查，不能互相替代。

## 子智能体审稿与盲测

在生成产物的上下文里，模型很难看出自己用了默认值；没有参与生成的检查者更容易发现。因此关键产物交给用户之前，先交给一个不继承本次对话的子智能体检查。

- **用哪种子智能体**：新建的子智能体（如 Harness 的 `subagent`），不用继承对话的 fork。截图审稿和盲测要求模型能看图；宿主支持选模时，选一个能看图、且与主 Agent 不同的模型。
- **隔离声明**：任务开头写明“这是独立检查：不要加载任何 Skill，不要读取工作区里的其他文件，只使用本任务给出的材料和工具”。
- **条件不满足时**：没有子智能体，或子智能体不能看图、不能调用所需工具时，跳过对应检查，由主 Agent 按同一份清单自查，并记录“未经独立检查”及原因。
- **结果怎么用**：子智能体只输出问题清单，不改文件。主 Agent 逐条修改，或写明保留的理由，处理完再交给用户。子智能体的结论不能代替用户确认、用户试玩或真机验证。

### 审稿

| 时机 | 交给子智能体 | 不给 |
|---|---|---|
| 步骤 1：卡片交给用户前 | 用户原话与参考、卡片文件路径、[游戏卡片](game-card.md#维度说明)的维度说明 | 对话历史、Agent 对设计的解释 |
| 步骤 2：HTML 交给用户前 | 各关键状态的截图和卡片；宿主没有浏览器工具时只能给源码，结论记为“未渲染” | 同上 |
| 步骤 6（可选）：对照卡片时 | 关键状态截图、文案表、卡片 | 同上 |

审卡片分两步，顺序不能颠倒：

1. **先预测默认值。** 只读用户原话，按维度说明逐项写出“不加约束时最可能的取值”。写完之前不打开卡片。
2. **再逐项比对。** 打开卡片，列出与预测重合的格子。重合处要有针对本作的理由，只套用锚点字眼的不算。

无论审什么产物，都请它逐项列出位置、问题和建议改法：

- 没写理由、或理由只是套用锚点字眼的选择；
- 用了维度说明中的常见默认值却没写理由的地方；
- 通不过置换测试的格子或文案；
- 产物与卡片关键状态表不一致的地方；
- 审卡片时：用户原话被改写的地方。

### 盲测

时机：步骤 6 中 P0 用例通过之后、请用户试玩之前。子智能体有浏览器操作能力时，也可以在步骤 2 盲测 HTML。

交给子智能体一份玩家操作说明，只写下面这些内容。任务写成“请直接开始玩”，不提示玩法：

- **入口**：MCP 下给同一进程内可用的 `handle`，没有时给存档路径，让它自己用 `qxqy_project_open` 打开；Harness 下给同一工作区中的存档。
- **可用动作**：`qxqy_studio_play` 的 `start`、`pointer`、`key`、`step`，以及 `qxqy_studio_play_screenshot`。点击用 `pointer`，按截图上的像素坐标点。`click` 按控件名触发，玩家看不到控件名，所以禁止；`get`、`history`、`runCase`、`saveCase`、`server*`、`qxqy_studio_get`、读文件和读日志会暴露状态、控件名或源码，也一律禁止。
- **推进时间**：以当前工具说明为准。MCP 试玩默认是 manual 时钟，不 `step` 时间就不走：`start` 时传 `canvasId: "mobile-16-9"`，之后每次 `step` 推进约 0.5 秒再截图，相当于慢放试玩。不要用 `realtime`：模型每次调用要好几秒，实时模式下来不及反应。
- **要求**：至少玩到一次结算，并重开一次。结束时不要 `stop`，试玩记录留给主 Agent 保存。
- **报告**：它认为目标是什么；第一次有效操作之前做过哪些尝试；哪里困惑或卡住；失败时是否明白原因；用自己的话描述感受（保留原话）；以及完整的工具调用清单。

主 Agent 先检查调用记录：宿主能提供时以宿主记录为准，否则看报告里的清单。出现禁止的调用，本次盲测作废并记录原因。有效的报告再与卡片的情感目标、关键词和 GDD 的 `HYPOTHESIS` 对照，偏差按 `bug / design / art-content` 归类。记录为 `runtime=simulator`，执行者记 `subagent-blind`。

能取到这次试玩的记录时，主 Agent 用 `history` 取出盲测的操作序列，用 `saveCase` 存成用例（如 `blind-1`），再 `stop`。盲测中卡住的地方可以用 `runCase` 回放复现；修复后用同一段操作回归。

## 产物位置与恢复

产物放在 `workspace/<slug>/`，下表路径相对于该目录：

| 产物 | 用途 |
|---|---|
| `docs/game-card.md` | 设计理念、风格维度和关键状态金样；步骤 1 锁定，后续步骤引用 |
| `docs/gdd.md`、按需 `docs/game-spec.md` | 玩法语义、范围与契约 |
| `docs/production-plan.md` | 当前步骤、知识来源与可用性、证据位置、未完成项和下一步 |
| `prototype/` | HTML 展示与操作说明 |
| `tests/` | 规则用例；测试 JSON 不是存档 |
| `docs/art-bible.md` | 把卡片风格落到参考图、目标素材和 UI 还原方案 |
| `main.lua`、`<slug>.save.json` | 源码与完整工程；存档开头附近有 `"format": "qxqy-simulator-save"` |
| `docs/tech-architecture.md` | 文件与控件职责、变量/信号、数据流和脚本挂载 |
| `docs/device-handoff.md` | 真机导入、真实索引、脚本路径与挂载、同步方式和待办；可并入已有交付说明 |
| `records/playtest.md`、`export/` | 试玩、审稿与修复证据，交付资产 |

试玩记录写明 `runtime=html|simulator|device`、执行者、步骤、期望与实际、未知项和修复后的回归。恢复时以实际产物和证据为准，不凭聊天摘要重做；用户已给的信息直接复用。

## 回退与完成

| 问题 | 回到 | 处理 |
|---|---|---|
| 设计或体验问题 | 步骤 1–2 | 更新卡片或 GDD，再更新步骤 3 的用例 |
| 风格或文案偏离 | 出现偏离的步骤；改方向时回步骤 1 | 按卡片修正；改方向先修订卡片，再同步 HTML、art-bible 和文案表 |
| 素材问题 | 步骤 4 | 记录目标 ID 与还原方案 |
| 规则或代码缺陷 | 步骤 3，再到步骤 5–6 | 补最小用例，再修复和回归 |
| 真机差异 | 步骤 7，再到受影响步骤 | 留存证据，修复后重新做真机验证 |

回退只加载受影响的步骤，不整套重跑。真机未验证时交付状态为“模拟器候选”；只有目标行为有真机证据时才标为通过。
