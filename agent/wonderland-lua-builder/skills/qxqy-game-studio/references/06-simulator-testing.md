# 6. 测试

本步骤回答：规则、布局和体验在模拟器里是否成立。

## 输入与适用时机

读取可运行的存档、源码、P0 与高风险用例、最近的缺陷和美术占位清单。工具接入和显式保存的要求同 [步骤 5](05-lua-implementation.md)。

## 执行动作

1. 运行 P0 和高风险边界用例。发现新缺陷时，先保留最小复现，再修复和回归。
2. Agent 亲自走一遍开局、首次成功、失败和重开：

   | 目的 | 工具 |
   |---|---|
   | 点击、按键、时间与用例断言 | `qxqy_studio_play` |
   | 静态布局截图 | `qxqy_studio_ui_screenshot` |
   | 运行画面截图 | 先 `play start`，再 `qxqy_studio_play_screenshot` |

3. 按五层证据检查布局与边界，并对照游戏卡片（见下文）。
4. P0 用例通过后、请用户试玩前，做一次[子智能体盲测](workflow.md#盲测)。
5. 请用户观察试玩或盲玩，按反馈分类处理。

### 五层证据

| 层 | 验证 | 证据 |
|---|---|---|
| L0 | JSON、路径、挂载、控件树 | 静态检查、`qxqy_studio_get` |
| L1 | 纯状态、计分、碰撞、生成、边界 | 纯函数/窄接口回放 |
| L2 | 输入→状态/日志/控件/变量/信号 | `qxqy-autotest` + `runCase` |
| L3 | 布局、层级、裁切、反馈、动画 | `qxqy_studio_ui_screenshot` / `qxqy_studio_play_screenshot` |
| L4 | 易懂、公平、节奏、触控、真机 | 观察式试玩、用户反馈、真机 |

HTML 展示不能替代本步骤的规则回归和画面检查。静态 UI 图片和元件图标在模拟器里能看到，要一起检查；只有其他图片来源显示缺失框时，不算视觉回归失败，记录目标 ID，到真机上看效果。

### 布局与边界

- **基准**：`mobile-16-9`（1280×720）整屏可见；PC 用同一设计板等比放大或留边。检查层级、裁切、反馈、文字和热区。HTML 截图或搜索结果不能当作模拟器试玩。
- **按玩法补充用例**：`edge-contact`、`input-spam`、`pause-resume`、`restart-twice`、`large-dt`、触控、服务端变量/信号，以及其余四种画布的 smoke。每个用例独立启动；切换画布会重建生命周期，用例之间不能串联状态。
- **发布候选另查**：五种画布、截图矩阵、控件/Lua/资源预算、资产清单和导出警告。

### 对照游戏卡片

- 逐个关键状态截图，对照卡片的关键状态表，检查色彩、强调层级、动效性格和文案。截图、文案表和卡片可以交给[子智能体审稿](workflow.md#审稿)。
- 文案表对照世界词表、长度预算和“不做”清单。
- 截图按卡片写明的主要设备选画布。MCP 截图不含动效的视频帧，用官方动效表现的反馈要在浏览器试玩里看。
- 偏离记为 `art-content`，按卡片修正；需要改方向时，回步骤 1 修订卡片。显示缺失框的图片不参与对照，留到真机检查。

### 观察试玩与反馈

- 先保存工程，再请用户试玩：MCP 下用 `qxqy_preview_open` 打开 Web 存档预览（MCP 与 Web 是两个进程，不保存就看不到改动），Harness 下在内置编辑器中试玩。请用户观察试玩或盲玩，看目标是否易懂、失败是否公平、节奏是否合适。
- 每轮只验证少量问题、只调少量变量，之后回归已稳定的规则。
- 反馈分为 `bug / design / art-content / platform / not-now`。缺失的官方图片保留 `targetId`，列入真机检查；显示缺失框不能证明资源不可用。

## 产物与完成条件

- 用例结果、截图、日志、盲测报告、缺陷处理结果、已知限制和导出警告；`records/playtest.md` 标为 `runtime=simulator`。
- P0 和相关边界已回归，未通过项已列出。
- 交付状态最多为“模拟器候选”。

## 下一步与回退

进入 [7. 真机试玩验证与 bug 修复](07-device-validation.md)。设计或体验问题回步骤 1–2；素材问题回步骤 4；规则或实现问题回步骤 3、5；平台未知项建立探针或交给步骤 7。只读取受影响步骤的文档。
