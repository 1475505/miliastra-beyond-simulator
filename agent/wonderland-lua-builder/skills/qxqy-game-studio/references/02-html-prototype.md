# 2. HTML 效果展示

本步骤回答：这样玩、这样看，用户认不认。

## 输入与适用时机

读取已锁定的游戏卡片和 GDD。演示要覆盖卡片关键状态表中的全部状态，表中已标出每个状态对应的 P0 用例。已有工程做窄修复时可以跳过本步骤，记录理由。

## 执行动作

1. 制作可直接打开的 `prototype/`，覆盖关键状态表中的全部状态：

   ```text
   prototype/index.html
   prototype/README.md    启动、操作、不可移植项、坐标差异
   ```

2. 按游戏卡片制作画面和文字：色板、造型语言、强调层级、运动性格、世界词表和文案金样都取自卡片，逐个状态对照卡片的关键状态表。
   - 卡片没有覆盖的元素做成不带风格的灰盒，并在 `prototype/README.md` 中列出；不要用渐变卡片、毛玻璃、emoji 图标、通用鼓励语等网页默认样式补齐。
   - 文字用模拟器同款的本机原神字体（见[字体说明](../../../../../studio/docs/local-fonts.md)），取不到时用系统黑体，不另选网页字体。特效只用来近似千星控件能做到的效果。
3. 交给用户前，做一次[子智能体审稿](workflow.md#审稿)，对照卡片检查演示；没有浏览器工具时只能审源码，结论记为“未渲染”。
4. 请用户试玩并判断：目标是否易懂、成功和失败的反馈是否清楚、节奏是否合适。如实记录试玩者和所用工具；Agent 没有浏览器操作工具时标 `browser-run: user`。结果记为 `runtime=html`。
5. 把画面与动画分为 `must-reproduce`、`can-degrade`、`concept-only`，写明哪些需要在千星中重新实现。
6. 试玩中规则有增改时，回写 GDD；风格或文案方向有变时，修订游戏卡片。

移植边界：HTML 的原点在左上、Y 轴向下，与千星相反。不复制 DOM/CSS 坐标，也不把 JavaScript 逐行翻译成 Lua。

## 产物与完成条件

- 可打开的 HTML 演示，以及启动与操作说明。
- `records/playtest.md` 记录了审稿结论、体验反馈和不可移植项。
- 用户已确认核心画面、操作与节奏；试玩中改动的规则已回写 GDD。
- 网页能玩只证明演示本身，不证明千星中可行。
