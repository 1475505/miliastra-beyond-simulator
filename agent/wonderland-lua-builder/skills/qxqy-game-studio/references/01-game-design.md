# 1. 策划案

本步骤回答：做给谁、玩家感受到什么、一局怎么玩。

## 输入与适用时机

输入：新游戏的想法、参考图、目标设备和用户约束。已有工程只补影响本轮任务的规则。先完成 [PREFLIGHT](workflow.md)。

## 执行动作

本步骤有两次用户确认，按顺序完成：

1. **游戏卡片：对齐设计理念。** 按 [游戏卡片](game-card.md) 写 `docs/game-card.md`；用户没给风格方向时，先给可比较的方向。交给用户前做一次[子智能体审稿](workflow.md#审稿)，再在对话中展示卡面，请用户确认。卡片标为 `locked` 后才进入下一项。
2. **GDD：锁定玩法规则。** 写 `docs/gdd.md`：唯一核心动词、最短循环、成功/失败/重开、PC 与手机输入、P0/P1/不做项、关键风险。请用户确认产品语义、P0、砍项和关键规则歧义；函数名、控件拆分和目录由 Agent 决定。

每条陈述标一种类型：`HYPOTHESIS`（靠试玩判断）、`CONTRACT`（可测试的规则）、`UNKNOWN`（需官方文档或真机证据）。玩法有真实分歧时，给出可比较的选项并推荐一个。

### 玩法规格

P0 的玩法契约写在 GDD。规则复杂时另建简短的 `docs/game-spec.md`；HTML 与 Lua 确需共用结构化规格时，才加 `prototype/game-spec.json`。规格只描述状态和玩家动作，不绑定 DOM 选择器、CSS 类或 JS/Lua 函数名。规格覆盖：

- 状态机：`boot → ready → playing → resolved(win|fail) → restart`；暂停属于 P0 时也要建模；
- 状态数据、生命周期，以及各状态以客户端还是服务端为准；
- 输入动作、前置状态、节流、热区、无效输入和结束后的输入；
- 显式 `dt`、位置/速度/碰撞边界、可注入的 seed 或序列；
- 成功/失败/重开、领域事件、稳定日志和错误降级；
- 每条不变量（INV）及其可观察的 oracle；
- 未知的平台事实，及其负责人和验证方式（探针或真机）。

## 产物与完成条件

- `docs/game-card.md` 已由用户确认（`locked`）。
- `docs/gdd.md` 已明确一局体验、P0 范围、输入和胜负语义，并经用户确认；按需附 `docs/game-spec.md`。
- 每个 `UNKNOWN` 都有证据来源或验证计划。
