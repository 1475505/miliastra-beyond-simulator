# 7. 真机试玩验证与 bug 修复

本步骤回答：游戏在真机上是否按预期运行。

## 输入与适用时机

读取模拟器候选版本、测试记录、资产清单、导出警告和已有的真机回传。用户给过的索引、画面和日志直接使用，只问缺项。

## 执行动作

### 准备交付说明

1. 整理 Lua、完整存档/GIA、目标素材 ID、测试结果和已知限制。
2. 在 `docs/device-handoff.md`（或项目已有的交付说明）中写本项目需要的操作：交付文件与版本、资产导入顺序、入口脚本与挂载对象、需要核对的控件/模板、脚本路径、试玩步骤与预期。只写本项目实际需要的事项。
3. 按本次导出格式核对脚本映射与挂载范围，见 [GIA 导出与脚本挂载](../../../../../studio/README.md#gia-导出与脚本挂载)；单独列出需要在千星沙箱中建立或复核的映射和挂载。已有工程复用已确认的配置，只说明本次变更和剩余操作。

导出文件的路径不能当作真机已导入的证据。

### 用户导入时需要完成什么

交接清单使用用户在编辑器中看到的控件/脚本名称和路径，不要求用户理解工具字段：

| 环节 | 用户操作 / 回传 | AI 配合 |
|---|---|---|
| 导入与挂载 | 导入本次所需的资产，核对脚本映射路径，把入口脚本挂到指定的客户端控件/容器节点或模板。已有的正确映射和挂载可以复用。 | 给出“哪个文件 → 哪个资产/挂载对象”的对应关系，以及本轮新增或变化的项。 |
| 核对真实索引 | 检查导入后目标控件/模板的实际索引；有变化时提供资产/控件名、原值（若已知）和新值，文字或截图均可。 | 按控件身份校准工程与脚本；复用已有回传，不重复索取。 |
| 绑定后续更新位置 | 希望以后用本机脚本同步更新时，确认账号、关卡和导入脚本目录；可从发现的候选目录中选择，或粘贴真实路径。 | 准备工作区源码与实机脚本的路径对应关系，保存配置并预览差异。 |
| 更新脚本 | 让 AI 更新已绑定的目录，或在 Web/DSH 的“Lua 脚本 → 实机脚本同步”中检查差异并确认复制；也可以手动更新。 | 完成源码与索引修复、保存工程，按授权同步并核对回执，指出新增脚本需要的映射/挂载。 |
| 保存与试玩 | 在千星沙箱中保存并重新试玩，按清单走开局、成功/失败、重开和本轮变更；回传出错的步骤、实际结果和相关画面/日志。 | 对照预期定位问题并修复，提供下一轮的更新与回归步骤。 |

绑定同步目录是可选项。无法访问本机目录时，交付 Lua 和明确的手动更新路径即可；真机验证不依赖目录绑定。

### 导入后的索引校准

用户可以用三种方式处理导入后的索引变化，无论哪种，AI 都要按实际修改核对一致性：

- **对话告知：** 用户给出目标资产/控件和真实的新索引，AI 修改模拟器中的索引和相关 Lua 引用。
- **在模拟器中修改：** 用户选中对应的客户端控件/模板，修改“索引”，AI 再按变更记录更新脚本。
- **直接改脚本：** 用户按交付说明修改索引常量或相关引用，并告知改动的文件；AI 读取实际差异，把实机/外部文件中的有效修改同步回工作区源码、存档源码和控件索引。脚本能运行不代表三者一致。

以真实编辑器中的索引为准，按当前模拟器接口的 `setControlGuid` / `controlGuidChanges` 流程处理。手工修改可能不产生记录，所以要按控件身份核对，不能只看记录是否为空：

1. 按资产和控件身份读取变更，把连续的 A→B→C 解析为最终索引；不要把模板索引和运行时控件 `Id` 混用。
2. 检查存档的 `scripts[].source`、路径源码、常量、配置表、别名和身份校验，把相关的语义引用同步为最终索引。非空的内联源码优先执行，不能只改外部 `.lua`。
3. 检查旧值是否还有残留；数值相同但无关的图片 ID 等保持不变。无法读取的源码或无法判定的引用标为待处理。
4. 相关引用全部同步、或确认没有引用之后，才用最新的 revision 调用 `acknowledgeControlGuidChanges` 确认对应记录；未处理的记录不要清除。
5. 显式保存完整存档，重启试玩，回归实例创建、身份检查和受影响的流程，再做真机验证。

完整的校准流程见 `qxqy-simulator` 操作说明；MCP 的工程操作还需要 `handle`，以当前 schema 为准。只改控件索引不会自动修复 Lua。

### 绑定导入后的脚本存储位置

先读取存档中已有的同步配置。没有时，由 AI 查找候选目录并请用户确认账号/关卡，或使用用户明确给出的路径；有多个候选时，不能只按最近修改时间猜测。

| 配置项 | 含义 |
|---|---|
| 项目脚本文件夹 `workspaceDir` | 本项目在工作区内的相对目录，例如 `workspace/my-game` |
| 千星沙箱脚本文件夹 `clientImportRoot` | 当前账号/关卡实际的 `external_lua_file/default_import_file` 绝对路径 |
| 游戏里的项目子文件夹 `clientSubdir` | 保留导入后脚本映射的相对路径，通常与工作区项目目录对应 |

例如源码为 `workspace/my-game/src/view.lua`，工作区目录和实机子目录都设为 `workspace/my-game`，目标路径就是 `<实机导入根目录>/workspace/my-game/src/view.lua`。保留目录层级，不按文件名平铺；路径变更后，核对真实编辑器的映射是否仍指向该文件。

这些路径都在运行模拟器服务的机器上；远程使用 Web/MCP 时，浏览器所在电脑的路径不是服务端可访问的路径。目录绑定随完整存档保存，不写入 GIA，也不是实时或双向同步。

### 后续让 AI 配合更新脚本

用 `qxqy_script_sync` 的 `discover/status/configure/save/preview/apply` 完成目录发现、配置、保存、预览和复制；MCP 的各次操作使用同一个 `handle`，Harness 在同一会话中完成。调用前以当前工具 schema 为准。

1. **对齐版本。** 核对索引变更、工作区源码、存档内联源码和已知的实机手改。内联 `source` 非空时优先，否则读取 `path`；只改磁盘文件，不等于同步的是新内容。只在实机上存在的修改，先比较并合并回项目；确有冲突再请用户判断。
2. **保存并预览。** 修复引用、确认已核验的变更后，用 `save` 保存完整存档（args 为 `path`、`expectedRevision`，已有路径时可省略 `path`；MCP 也可用 `qxqy_project_save`），再用 `preview` 核对每个脚本的来源、目标和新增/覆盖内容。复制之前不能说“已同步到真机”。
3. **按授权复制。** 用户要求更新已绑定的目录时，选择无错误且有变化的脚本，用 `apply` 提交 `{ planId: preview.id, scriptIds: [...], confirmed: true }`，不必再让用户去编辑器点击确认。用户只要求绑定或查看差异时，不执行复制。计划过期就重新预览；计划不能跨工程或跨进程使用。旧宿主没有 save/apply 时，请用户升级，或在 Web/DSH 编辑器中加载同一存档、重新预览后手动确认；不要用 shell、手工调用端点或目录联接绕过接口校验。
4. **核对回执再试玩。** 记录每个脚本的成功/失败和备份位置。同步只覆盖存档登记的 Lua 脚本（含未挂载的 require 模块），不是整个目录的镜像；新增脚本仍要在真实编辑器中建立映射和必要的挂载，UI/模板结构有变化时按实际情况重新交付资产。用户在千星沙箱中保存并试玩之后，才能确认加载的是本轮源码。

用户选择手动更新时，给出本次改动的文件和准确的目标路径，提醒保留实机上已有的修改；手改完成后，把最终版本同步回项目，以免下一轮被旧存档覆盖。“已复制到磁盘”“编辑器已保存/重新加载”“真机已验证”分开记录；不承诺“绑定一次，以后自动生效”。

### 缺陷修复与回归

- 请用户按交付清单实际试玩，记录真机环境、操作步骤、期望与实际、截图/日志和可复现性；证据标 `runtime=device`，注明执行者或来源。没有真机结果的行为保持未验证，模拟器截图不能充当真机结果。
- 为每个真机缺陷建立最小复现，归类为 Lua、素材、布局、模拟器差异或平台未知。先更新用例或写明人工检查项，再修复，然后重新做模拟器和真机验证；保留修复前后的证据。

## 产物与完成条件

- 游戏资产、导入/挂载与实际索引记录、脚本路径与更新方式、同步或手动更新的结果、真机记录和修复记录。
- 未完成的导入、挂载、引用修复、复制或真机检查，逐项列为待办。
- 只有真机证据覆盖的目标行为才标为通过；其余项明确列出，交付状态保持“模拟器候选”。

## 下一步与回退

目标行为有真机证据、缺陷已闭环时，本轮交付完成。规则或代码缺陷回 [步骤 3](03-test-cases.md)、[步骤 5](05-lua-implementation.md)和 [步骤 6](06-simulator-testing.md)，素材问题回 [步骤 4](04-art-assets.md)。按项目的知识维护规范沉淀证据，区分官方文档、真机观察、模拟器策略与假设。
